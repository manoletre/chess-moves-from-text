      About the model

      Why a model, and not a regular expression?

      Because e4 is a move in White played e4, a square in the pawn on e4, and part of a series in the game continued Nb8 Nf3 e4. Only the context tells them apart.

      What it does

      The tagger reads a piece of text and labels every chess reference in it with one of six types, returning exact character positions. It only detects. Turning the detections into links, board highlights and move replays is the job of the app that uses it: chess-tutor, an AI chess tutor whose explanations become interactive.

      TypeExampleIn the app, clicking it…
      STARTprefers Qxd5plays the move from the current position
      CONTcontinued Nb8 Nf3 c6replays the series up to that move
      SQUAREthe pawn on d5highlights the square
      FILEthe c-file is openhighlights the column
      RANKa rook on the 7th rankhighlights the row
      DIAGONALthe a1-h8 diagonalhighlights the diagonal

      The current position is the one before the move being discussed. A single move is a START with nothing after it; a series is a START followed by CONTs. Vague references like the long diagonal or the back rank are deliberately left unlabelled.

      How it works

      1. Tokenize. The text is split into tokens: Qxd5 becomes  Q x d 5.
      2. Encode. LFM2.5-Encoder-230M reads all tokens at once, in both directions, and turns each one into 1024 numbers describing it in context.
      3. Classify. A small head (a 1024 × 13 linear layer) scores 13 labels per token: O plus B-/I- (first/other token) for each of the six types.
      4. Decode. Tokens are merged back into character spans, and stray punctuation like , !? ** is trimmed, keeping + # =.

      Trained end-to-end on 1,000 synthetic examples: real legal positions from python-chess dropped into chess-tutor-style sentences, with look-alikes (A4, Room B12, the PGN file) mixed in as negatives. 8 epochs on a Colab T4.

      How well it works

      Test set: 184 texts the model never trained on. 150 come from sentence templates held out of training; 34 are hand-written, including real chess-tutor output. A span counts only if its start, end and type are all exactly right.

      Known limitations

      • It almost never misses a reference; mistakes are about the type. Unfamiliar phrasings like only after dxe5 play h4 can make a CONT look like a START.
      • A square named with a verb right after a series (…Nxe5, the knight eyes f7, hitting d5) is often read as the next move of that series; the pawn on d5 is recognised correctly.
      • A square at the start of a list (squares like d8 and c1) is sometimes read as a move.
      • Castling written with zeros (0-0) and move numbers after results (0-1; 9. Bxb5) can confuse it.
      • It can't express side branches, or lines that start somewhere other than the current position. The app should replay each series and only link it if every move is legal.
      • Ranks are often counted from the speaker's side (Black's 7th rank is White's 2nd).

      Use the API

      curl -s localhost:8000/api/tag \
  -H 'content-type: application/json' \
  -d '{"text": "The game continued Nb8 Nf3, and the pawn on d5 falls."}'
      {
  "spans": [
    {"start": 19, "end": 22, "type": "START", "text": "Nb8", "series": 0, "index": 0},
    {"start": 23, "end": 26, "type": "CONT",  "text": "Nf3", "series": 0, "index": 1},
    {"start": 44, "end": 46, "type": "SQUARE", "text": "d5"}
  ],
  "series": [[…Nb8, …Nf3]],
  "highlights": [{…d5}],
  "truncated": false
}

      Texts longer than 512 tokens are cut off (truncated: true). Everything runs locally on CPU; the model is about 920 MB and uses about 1.1 GB of memory.
